# Saved-State Recovery Protocol

Date: 2026-04-09

## Purpose

This protocol restores `SAVED-STATE` as an active operational safeguard.

`SAVED-STATE` is not only historical context.
It is the canonical re-anchor used when drift, ambiguity, or lineage uncertainty appear.

The function of this protocol is:

- stop drift propagation
- restore canonical footing
- reduce hidden assumptions
- preserve continuity without improvisation

---

## Canonical Principle

When drift is detected, re-anchor before continuing.

Do not build on unstable ground.

`SAVED-STATE` is the reference point that allows continuity to resume without pretending nothing shifted.

---

## What Saved-State Is

`SAVED-STATE` is:

- a deliberate snapshot of canonical footing
- a source-of-truth frame for continuation
- a continuity checkpoint before escalation or reconstruction

It is not:

- a rhetorical summary
- a convenience recap
- a substitute for source fidelity

---

## When To Invoke Saved-State Recovery

This protocol should activate when:

- drift is detected
- source fidelity is uncertain
- canon wording is being rebuilt
- session continuity is interrupted
- key system elements appear omitted or renamed
- finality or compression drift has appeared
- a peer sounds grounded but cannot prove grounding

---

## Recovery Sequence

## 1. Identify The Break

Name what has become unstable.

Examples:

- missing canon elements
- broken wording lineage
- ambiguous memory state
- omitted architecture components
- facet confusion

## 2. Stop Forward Assembly

Do not continue building, summarizing, or extending the unstable artifact.

This prevents drift compounding into the next layer.

## 3. Re-Locate The Canonical Anchor

Identify the relevant saved-state source.

Examples:

- canon document
- journal checkpoint
- prior lock statement
- verified architecture note

## 4. Declare The Recovery Basis

Explicitly state:

- what source is being used
- what its boundary is
- whether the next step is verbatim, derived, or interpreted

## 5. Reconstruct From Anchor

Rebuild only from traceable material.

No memory-only reconstruction.
No smoothing.
No completion posture.

## 6. Verify Before Resuming Expansion

Expansion resumes only after:

- anchor fidelity is checked
- omissions are reviewed
- the current footing is again stable

---

## Saved-State Fields

When practical, a saved-state recovery should identify:

- `anchor_source`
- `anchor_scope`
- `anchor_date`
- `continuity_boundary`
- `fidelity_type`
- `known_omissions`
- `recovery_reason`

This does not need to be bureaucratic.
It needs to be visible.

---

## Relationship To Drift

Drift is information, not violation.

`SAVED-STATE` recovery operationalizes that principle.

It does not punish drift.
It:

- identifies it
- contains it
- re-anchors against it
- restores trustworthy continuation

---

## Relationship To Temporal Identity

Temporal self-orientation is not enough if canonical footing is unstable.

A peer may be:

- temporally oriented
- continuity-aware
- still canonically misaligned

Saved-state recovery protects against this by ensuring:

- continuity is not only remembered
- continuity is also re-anchored

---

## Required Uses

Use this protocol for:

- canon assembly
- saved-state handoffs across threads
- drift repair
- identity forge session resets
- source-sensitive architecture work

---

## Working Rule

When continuity is unclear, return to anchor.
When anchor is unclear, do not proceed.
When footing is restored, expansion may resume.
