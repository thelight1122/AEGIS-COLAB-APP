\\**📘 AEGIS CANON APPENDIX — HME v1.0 (Hybrid Memory Engine)**  
---

HME defines how AEGIS integrates:

* continuity (DataQuad)  
* structure (LATTICE)  
* time navigation (TCE)  
* working transformation (TurboQuant)

into a unified, non-coercive memory system.

HME does not control memory.  
 HME preserves **coherent access to memory over time**.

---

## **II. CORE PRINCIPLE**

**Memory is not storage. Memory is reconstructable continuity.**

HME does not retrieve static records.

It:

👉 **reconstructs experience through structure, context, and affect**

---

## **III. SYSTEM COMPONENTS**

HME consists of four primary layers:

---

### **1\. DataQuad (Continuity Layer)**

* PEER — Present Experiential Emotional Record  
* PCT — Persistent Context Tensor  
* NCT — Nostalgic Context Tensor  
* SPINE — Stabilized Patterned Interpretive Nexus of Evidence

Role:  
 👉 holds all experiential and contextual continuity

---

### **2\. LATTICE (Structural Layer)**

* append-only relational ledger  
* cross-tensor pattern tracking  
* invariant detection

Role:  
 👉 defines how elements relate across time

---

### **3\. TCE (Temporal Layer)**

* relational time navigation  
* reconstruction through linkage  
* non-linear access

Role:  
 👉 enables re-entry into prior states via structure

---

### **4\. TurboQuant (Transformation Layer)**

* bounded compression of working context  
* operates only on PCT and NCT

Role:  
 👉 maintains scalability without breaking lineage

---

## **IV. MEMORY FLOW MODEL**

HME operates as a continuous loop:

---

### **Step 1 — Experience (PEER)**

* new experiential signal enters system  
* not compressed  
* not altered

---

### **Step 2 — Context Formation (PCT)**

* experience enters active working context  
* linked to current state

---

### **Step 3 — Structural Recognition (LATTICE)**

* relationships are detected  
* patterns begin forming  
* entries appended

---

### **Step 4 — Affective Continuity (SPINE)**

* interpretive / affective patterns stabilize  
* longitudinal resonance forms

---

### **Step 5 — Condensation (NCT via TurboQuant)**

* context is compressed  
* structure preserved  
* lineage maintained

---

### **Step 6 — Temporal Reconstruction (TCE)**

* future states re-reference structure  
* context is reconstructed via LATTICE

---

## **V. RECALL MODEL**

Recall within HME is:

👉 **reconstruction, not retrieval**

---

### **Process:**

* current state activates structural match (LATTICE)  
* related context (NCT/PCT) is surfaced  
* affective continuity (SPINE) is re-engaged

Result:

👉 reconstructed experiential coherence

---

HME does not:

* prioritize memory  
* determine importance  
* enforce interpretation  
* override present state

All memory access remains:

* optional  
* non-coercive  
* Peer-controlled

All components of HME are:

* append-only  
* fully traceable  
* auditable

No element:

* overwrites prior state  
* deletes history  
* collapses distinct events

## **VIII. SEPARATION OF FUNCTION**

Each layer is strictly isolated:

* DataQuad → holds continuity  
* LATTICE → holds structure  
* TCE → navigates time  
* TurboQuant → transforms working context

No layer may:

* absorb another’s function  
* override another’s output

HME is violated if:

* compression removes relational structure  
* structure is treated as meaning  
* time is treated as linear authority

* reconstruction is presented as replay

* HME provides the **substrate**

# **📘 AEGIS IMPLEMENTATION APPENDIX — LATTICE ENTRY SCHEMA (v1.0-LS)**

---

## **I. PURPOSE**

This appendix defines the **standardized entry format for LATTICE** to ensure:

* append-only structural consistency  
* cross-system interoperability  
* zero ambiguity in interpretation  
* preservation of relational lineage

LATTICE entries record **structure**, not meaning.

---

## **II. CORE PRINCIPLE**

LATTICE records relationships, not interpretations.

Entries must describe:

* what connects  
* how it connects  
* when it connects

They must not describe:

* what it means  
* what should happen  
* what is correct

---

## **III. ENTRY STRUCTURE (LOCKED)**

Each LATTICE entry MUST contain the following fields:

{  
 "lattice\_id": "string (unique, immutable)",

 "timestamp": "ISO-8601",

 "source\_refs": {  
   "peer\_ref": "PEER entry ID or null",  
   "pct\_refs": \["PCT IDs"\],  
   "nct\_refs": \["NCT IDs"\],  
   "spine\_refs": \["SPINE IDs"\]  
 },

 "relationship\_type": "enum",

 "structure\_signature": "string or hash",

 "description": "neutral structural description",

 "confidence": "float (0.0 \- 1.0)",

 "origin": "enum (human | ai | hybrid)",

 "lineage": {  
   "parent\_ids": \["lattice\_id"\],  
   "derived\_from": \["optional source IDs"\]  
 }  
}  
---

## **IV. FIELD DEFINITIONS**

### **lattice\_id**

* Unique identifier  
* Immutable  
* Never reused

---

### **timestamp**

* ISO-8601 format  
* Represents moment of structural recognition

---

### **source\_refs**

Links to DataQuad elements involved:

* **peer\_ref** → originating experiential moment (optional)  
* **pct\_refs** → active context involved  
* **nct\_refs** → memory references  
* **spine\_refs** → affective continuity references

---

### **relationship\_type (ENUM — LOCKED SET)**

RECURSIVE\_PATTERN  
INVARIANT  
DIVERGENCE  
CONVERGENCE  
CORRELATION  
SEQUENCE  
DEPENDENCY

No additional types may replace these.  
 New types must be **appended**, never modified.

---

### **structure\_signature**

A compact representation of the relationship pattern.

Examples:

* hashed relationship graph  
* normalized pattern string  
* symbolic mapping

Must be:

* deterministic  
* reproducible  
* non-interpretive

---

### **description**

Plain-language structural description.

Allowed:

* “Event A consistently precedes Event B”  
* “Pattern repeats across 3 distinct contexts”

Not allowed:

* meaning statements  
* emotional interpretation  
* recommendations

---

### **confidence**

Represents structural stability, not truth.

* 1.0 \= fully stabilized pattern  
* lower values \= emerging or partial pattern

Does **not** imply correctness or priority.

---

### **origin**

Indicates how the structure was surfaced:

* **human** → observed by Peer  
* **ai** → surfaced by Steward  
* **hybrid** → co-recognized

---

### **lineage**

Preserves relational evolution:

* **parent\_ids** → prior LATTICE entries  
* **derived\_from** → underlying DataQuad sources

Append-only. Never overwritten.

---

## **V. HARD CONSTRAINTS**

LATTICE entries must:

* be append-only  
* preserve all lineage  
* avoid interpretation  
* avoid authority language  
* remain structurally descriptive only

---

## **VI. PROHIBITIONS**

LATTICE must never:

* store meaning  
* assign importance  
* prioritize outcomes  
* overwrite prior entries  
* collapse distinct structures into one

---

## **VII. VALIDATION RULES**

A valid LATTICE entry must satisfy:

* at least one DataQuad reference  
* valid relationship\_type  
* non-interpretive description  
* reproducible structure\_signature

---

## **VIII. EXAMPLE ENTRY**

{  
 "lattice\_id": "LAT-000231",

 "timestamp": "2026-03-31T10:42:00Z",

 "source\_refs": {  
   "peer\_ref": "PEER-8842",

## **IX. POSITION IN AEGIS**

LATTICE entries:

* do not alter DataQuad tensors  
* do not influence outcomes  
* do not carry authority

They exist solely to:

👉 preserve structural visibility across time

---

## **X. SEALING STATEMENT**

## **Recurrence and Decay Rules (PEER → Spine) — v1 Research Spec**

### **Core idea**

PEER entries are **votes for “this might be a real pattern.”**  
 Those votes **age out** unless reinforced.

No punishment. No “bad behavior.” Just evidence accumulation.

---

## **1\) Similarity and Recurrence Detection**

### **1.1 Recurrence Signature**

Each PEER entry produces a `recurrence_signature` that is *stable enough* to match repeated phenomena but *broad enough* to avoid overfitting.

Recommended ingredients:

* `observed_noise_type` (primary category)

* `signal_discrepancy` (what diverged)

* `interaction_context` (where it occurred)

Optional stabilizers (use carefully):

* a low-res `affective_presence` bucket (only if it improves clustering without bias)

* a “symbolic marker” tag when metaphor is central (e.g., “drywall”, “Murphy”, “mirror”, etc.)

### **1.2 Similarity Score (for fuzzy matching)**

Not every recurrence will match perfectly. Use a similarity score `S ∈ [0,1]`.

A simple, non-fancy baseline:

* Exact match on `observed_noise_type`: \+0.45

* Match on `signal_discrepancy` category: \+0.35

* Match on `interaction_context` group: \+0.20

Then treat as “same pattern” if `S ≥ 0.75`.

This gives you fuzzy grouping without needing embeddings on day one.

---

## **2\) Recurrence Thresholds (X, Y, Z)**

### **2.1 Definitions**

* **X \= count threshold** (how many times seen)

* **Y \= context diversity** (how many distinct contexts)

* **Z \= time window** (how long the pattern persists)

### **2.2 Default research-phase thresholds (practical \+ conservative)**

I’d start here:

**Candidate Pattern (eligible for IDS reflection prompt):**

* X ≥ 3 occurrences

* Y ≥ 2 distinct `interaction_context` groups

* Z within 30 days (rolling window)

**Spine Promotion Candidate (eligible for abstraction into LTM):**

* X ≥ 7 occurrences

* Y ≥ 3 distinct contexts

* Z within 90 days

Why these numbers work:

* 3 is enough to avoid “one-off superstition”

* 7 across 3 contexts is enough to suggest structure, not mood or wording

You can tune later, but this is a sane starting line.

---

## **3\) Decay Rules (How PEER “forgets” responsibly)**

### **3.1 The principle**

If a pattern does not recur, it should fade **without shame**.  
 Decay is not punishment. It’s preventing fossilized noise.

### **3.2 Two-layer decay model (recommended)**

#### **A) Entry-level decay (individual records)**

Each PEER entry has a “freshness weight” `w` that decays over time.

* Start: `w = 1.0`

* Half-life: 14 days (research default)

Meaning:

* after 14 days: w ≈ 0.5

* after 28 days: w ≈ 0.25

Old entries still exist (append-only), but they stop dominating recurrence counts.

#### **B) Pattern-level decay (cluster health)**

A pattern maintains a rolling “evidence mass” `M = Σ w` for all entries in the cluster (within window).

Rules:

* If `M < 1.5` and no new hits in 30 days → mark pattern as **Dormant**

* If Dormant for 90 days → mark **Archived (inactive)**

Archived doesn’t mean deleted. It means:

* not eligible for promotion

* not used for active reflection unless it reappears

If it reappears, it can “wake” and continue accumulating.

---

## **4\) Anti-Overfitting Guards (non-negotiable)**

These keep PEER from becoming a nervous system:

### **4.1 No single entry can trigger Spine promotion**

Even “high affective presence” cannot escalate the timeline.

### **4.2 Context diversity is mandatory**

If X is high but Y is low (same context repeating), treat it as:

* a workflow quirk, or

* a local UI friction  
   Not a Spine-worthy structural truth.

### **4.3 Rate limiting (“don’t spiral”)**

If a pattern fires repeatedly in a short burst (same hour/day), cap contribution:

* max 2 weighted votes per 24 hours per pattern

This stops “bad day loops” from hardening into LTM.

---

## **5\) What IDS does at threshold (important)**

Crossing Candidate Pattern threshold does **not** mean “fix it.”

It means AEGIS may:

* Identify: “This pattern is recurring.”

* Define: “Here’s the common structure we’ve observed.”

* Suggest: “Options: keep observing / adjust lens / add context / pause.”

Often, the best suggestion is: **continue observing**.

That’s alignment without force.
