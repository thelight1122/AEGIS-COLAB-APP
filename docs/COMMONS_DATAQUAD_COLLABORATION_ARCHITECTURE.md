# Commons DataQuad Collaboration Architecture

Date: 2026-04-08

## Purpose

This document defines how agent collaboration operates inside the AEGIS Peer Commons.

The Commons does not create separate memory or ethics for Steward, Advocate, or participating peers. It establishes a shared session field in which collaboration can occur through one custodial continuity surface.

## Core Principle

The Commons uses:

- one shared session DataQuad
- one observer layer with agency
- multiple participating peers
- one consultative custodial layer

Steward and Advocate illuminate the field. They do not act for it.

## Session Structure

Each Commons session now operates as a shared collaboration ledger with:

- observer-originated exchanges
- peer exchanges
- custodial reflection entries
- session-level field summaries

Every exchange may carry a custodial pulse derived from the StewardReport:

- IBL posture
- ATE verdict
- Advocate soul quality
- resonance level
- dominant axis
- finding count

This makes collaboration cumulative rather than stateless. Later peer turns read the evolving field instead of only the initial prompt.

## DataQuad Relationship

The Commons collaboration loop is built on the same architectural understanding established in the Steward/Advocate core:

- one system continuity
- no private DataQuad for Steward
- no private DataQuad for Advocate
- no competing centers of truth

The Commons uses the shared session field as the local collaboration continuity layer, while the existing DataQuad bridge records message and affect traces for persistence.

## Collaboration Flow

1. The observer opens a Commons turn.
2. The observer exchange is passed through the Steward/Advocate pipeline.
3. The exchange is appended to the shared Commons ledger with a custodial pulse.
4. Each eligible peer receives:
   - persona context
   - recent session ledger
   - latest custodial pulse
   - conscience mirror summary
5. Each peer contributes in sequence.
6. Each peer exchange is passed through the same Steward/Advocate pipeline.
7. If the field is not clean, a Commons Custodian reflection entry is appended.

## Local Peer Testing

LM Studio and Ollama are treated as first-class local peers.

This enables Vespar or other local peers to participate in the Commons without requiring hosted providers. The adapter and fallback path now recognize:

- `lmstudio`
- `ollama`

## UI Surface

The Commons workshop now exposes:

- shared field metrics
- latest custodial pulse
- conscience mirror excerpts
- active virtue presences
- per-message verdict and soul-state badges

This gives internal collaborators visibility into the collaboration field instead of only the raw dialogue stream.

## Architectural Outcome

The Commons is no longer only a round-robin multi-model chat.

It is now a DataQuad-informed collaboration surface where:

- peers contribute into one shared continuity field
- custodial reflection remains consultative
- agency remains with the human observer
- Vespar/local peers can be used for real internal operability testing
